# VahanKhata — Master System Mindmap & Agent Reference

> **Purpose:** This file serves as the definitive architecture map, routing table, and protocol guide for AI coding agents (Cline / Roo Code) working within the `VahanKhata` repository. Refer to this document first to avoid exploratory file searches and save context tokens.

## Stack
- Backend: Python 3.12, FastAPI, uvicorn, reportlab (PDF), psycopg2-binary, python-dotenv.
- Database: Managed PostgreSQL (Neon DB). No ORM, no Alembic. Schema lives only in `/database/schema.sql` (+ `/database/incremental.sql`). The app never runs DDL.
- Frontend (legacy): The server-rendered HTML f-string pages (Tailwind CDN) were **removed from the served app** (`main.py` no longer mounts them). All UI now lives in the two React SPAs — the **app** (`frontend/`) and the **public marketing site** (`public-site/`); the backend is a **pure JSON API** (optionally serving the built SPA via a conditional mount — see Entry Point). See `MIGRATION_JSON.md`.
- **Frontend (new, Phase 1):** `frontend/` — **Vite + React 18 SPA** (React Router v6, Tailwind v3 pre-built via PostCSS). Builds to `frontend/dist/`. Consumes only `/api/v1/*` JSON endpoints.
  - Build: `cd frontend && npm install && npm run build` → outputs `dist/`.
  - Dev: `npm run dev` (proxies `/api` → `http://localhost:10000`).
  - **Deploy:** standalone **Static Site** `vahankhata-app` on Render (publish `frontend/dist`). The SPA uses **relative** `/api/v1/*` paths against `VITE_API_BASE_URL` (same-origin `""` for single-container Docker, or the cross-origin API URL on Render); `api.js`'s `API_BASE_URL` defaults to `""` — never `http://localhost:8000`, which breaks production auth (401).
  - Routing note: it is a **pure client-side SPA** (Vite) — dynamic routes like `/trips/:tripCode` resolve client-side via React Router, NOT server-side.
  - **Pages (app only):** `/` (the **login page** — now the default entry point; redirects to `/dashboard` when already authenticated, file `src/pages/index.jsx`), plus the **Authenticated app:** `/dashboard`, `/trips`, `/trips/:tripCode`, `/trips/new` (trip_manager/super_admin — Start New Trip form posting to `POST /api/v1/trips`, prefills vehicle/driver from `/api/v1/vehicles` + `/api/v1/drivers`), `/settlements` (Settled Trips PDF listing), `/change-password` (all roles), `/drivers` (trip_manager/super_admin) — shows each driver's **batta profile (type + rate)**; **driver-only** `/driver-salary` (read-only salary/batta view), plus **Super Admin** `/fleets`, `/users`, `/vehicles`, `/benchmarks` (role-guarded via `<ProtectedRoute>`). `/subscription` (renamed from `/billing`; old `/billing` path redirects to `/subscription`) and `/trips/:tripCode` are restricted to `trip_manager`/`super_admin` via the inline `roles` guard. CRUD pages call the `/api/v1/*` create/update/toggle endpoints directly.
- **Public marketing site (new, standalone):** `public-site/` — its **own static Vite + React 18 SPA**, deployed as a separate Render **Static Site** `vahankhata-site` (publish `public-site/dist`). No auth, no `/api` dependency (the contact form builds a client-side `mailto:`/WhatsApp link). Routes: `/` (landing), `/about`, `/why-us`, `/features`, `/pricing`, `/faq`, `/contact` (also `/request-demo` reuses the Contact page), `/privacy`, `/terms`, `/security`, `/cookies`, plus a `*` 404. Shared primitives in `public-site/src/public/` (`PublicLayout`, `PublicNav`, `PublicFooter`, `Seo` (per-page title/OG/canonical), `UI.jsx` (PageHero/Prose/CTABand/IconChip/SectionHead), `public.css` (theming via `:root` CSS vars flowing from `tailwind` brand/ink tokens)). `public-site/src/config.js` exports `app(path)` which builds every **"Log in"** link from a hard-coded app origin `https://app.vahankhata.in` — internal marketing links stay relative.
- **Phase 0 JSON API (new):** `/api/v1/*` transport-agnostic endpoints, now split into one router per domain in `backend/app/api/v1/` (`dashboard.py`, `auth.py`, `trips.py`, `expenses.py`, `vehicles.py`, `fleets.py`, `users.py`, `benchmarks.py`, `billing.py`); `backend/app/api/api_v1.py` is the aggregator that mounts them all under one `/api/v1` prefix. Reuses `db/queries/*` — no business-logic duplication. Serves the React SPA + hybrid/mobile app; the legacy HTML pages still work unchanged.

## Transport-Firm & Entitlement Model (implemented)
- **Model:** a `fleets` row = a transport firm (the tenant). It owns the subscription entitlement, its staff (`users.fleet_id`), its vehicles and trips.
- **Plan capability matrix:** `subscription_plans.features` JSONB (e.g. `{"vehicle_limit":1,"driver_limit":5,"whatsapp":true}`) replaces the single vehicle limit as the source of product capability. Extensible: new product dimensions are data edits, not migrations.
- **Fleet add-ons:** `fleets.entitlement_addons` JSONB holds bought extra capacity (e.g. extra vehicle slots); `fleets.is_default` marks the exactly-one default-fleet anchor (G5/G7).
- **Staff position:** `users.fleet_role` (`owner`/`manager`/`branch_head`/`driver`) sits inside a firm alongside the platform `role`.
- **Audit ledger:** `fleet_billing_events` (PLAN_CHANGE/EXTRA_SLOT/TRIAL_START/PAYMENT) — each entitlement mutation is append-only explainable (G6/G10).
- **Entitlement resolver:** `backend/app/services/entitlements.py::fleet_feature()` merges plan + add-ons; `fleet_can_add_vehicles()` distinguishes `NOT_ENTITLED` vs `VEHICLE_LIMIT` (G3). `vehicles.py` now routes the vehicle gate through it.
- **Onboarding wizard:** `POST /api/v1/fleets/onboard` (`backend/app/api/v1/onboard.py`) — creates fleet + owner Trip Manager + trial (+ optional first vehicle/driver with batta/capacity profile) in one transaction; dispatches the owner's welcome email (same as Path A) and returns inline `payment_url` for paid plans + `email_queued` flag (G2). **Resilient TRIAL-plan resolution (2026-08):** `db/queries/fleets.py::insert_fleet` and `start_trial_subscription` now resolve the TRIAL `subscription_plans` row in Python (`_trial_plan`) and fall back to the `TRIAL_VEHICLE_LIMIT` default (1) when the catalogue is unseeded — a missing seed row previously wrote `NULL` into the NOT NULL `fleets.vehicle_limit` and raised a 500 NotNullViolation on onboard/trial-activate. `database/incremental.sql` also idempotently re-inserts the TRIAL plan row.
- **Fleet picker:** `POST /api/v1/users` accepts optional `fleet_id` when `role=="trip_manager"` (G1).
- **Billing health:** `GET /api/v1/fleets/{fid}/billing` was **removed (2026-08 dead-code cleanup)** — it had no SPA/API consumer; the vehicle gate flows through `services/entitlements.py::fleet_can_add_vehicles()` instead.

## Route Guards — single JSON auth path
- **`/api/v1/*` JSON endpoints**: use `security.require_json_auth` / `require_json_role` → they return **401/403 with a JSON body** (`{"error", "code"}`). Never a 303 redirect — client fetch()/axios cannot consume redirects, and public marketing pages must never be yanked to `/login`.
- **Legacy redirect guards removed:** `security.require_auth` / `require_role` (303 → `/login`) and the `_auth`/`UnauthorizedRedirect` helpers have been **deleted** as dead code — the legacy HTML routers that used them are no longer registered. All live routes are JSON-guarded only.
- **Auth sources:** a request is authenticated by the `ff_auth_session` cookie **OR** an `Authorization: Bearer <token>` header (both resolve through the same in-memory session store). `get_current_user()` checks both. This is how web + mobile share one backend.
- **CSRF:** the never-wired helpers (`issue_csrf_token` / `validate_csrf_token` + the `_csrf_tokens` store) were **deleted (2026-08 dead-code cleanup)**. `/api/v1/*` JSON mutations rely on Bearer-in-header + JSON content-type; do not reintroduce single-use CSRF tokens into api_v1 (React parallel requests would race).

## Database Access Pattern (Postgres/Neon)
- Connection: `psycopg2.connect(os.getenv("DATABASE_URL"), cursor_factory=psycopg2.extras.RealDictCursor)`.
- JSONB params are always passed as `psycopg2.extras.Json(...)` or `json.dumps(...)` — never a raw Python `dict` (`fleets.log_fleet_billing_event`, `billing.webhook_logs`).
- `trips` deliberately has NO `updated_at` column; there is no `trg_trips_updated_at` trigger (older schema.sql created one, which broke every `UPDATE trips` — dropped in `schema.sql` + `incremental_ddl.sql` and `incremental_dml.sql`).
- Global `DEC2FLOAT` type caster registered at startup so `NUMERIC` columns arrive as Python `float`, not `Decimal`.
- Placeholders: `%s` only (never `?`).
- `created_at`/timestamps are native `datetime` objects — always format via `fmt_dt(dt)` helper, never slice (`dt[:16]` crashes).
- No `init_db()` / DDL in the app — schema + seed data are applied manually to Neon from `/database/schema.sql`.

### Core Tables (see [/database/schema.sql](/database/schema.sql))
- `subscription_plans` (id, code UNIQUE: TRIAL/MONTHLY/YEARLY, name, billing_cycle, trial_days, price, vehicle_limit, is_active) — product catalogue. TRIAL = 15 days/₹0/1 vehicle; MONTHLY = ₹799/1 vehicle; YEARLY = ₹7,191 (25% off)/1 vehicle.
- `fleets` (id, owner_name, phone UNIQUE, email, plan_id FK→subscription_plans, subscription_status: TRIAL/ACTIVE/PAST_DUE/CANCELLED/EXPIRED, trial_started_at, trial_ends_at, vehicle_limit, next_billing_date, razorpay_subscription_id, razorpay_customer_id, is_active, created_at/updated_at). Owns the subscription entitlement — trial clock, vehicle cap, and Razorpay billing references. **Denormalized `subscription_plan` / `plan_rate` removed (2026-08)** — `plan_id` is the single source; code/price derive via JOIN with `subscription_plans`.
- `users` (id, username UNIQUE, password_hash, full_name, role: super_admin/trip_manager/driver, phone, email, fleet_id FK→fleets ON DELETE CASCADE, is_active, batta_type DEFAULT 'FIXED_TRIP' CHECK (FIXED_TRIP/PER_KM/DAILY/NONE), default_batta_rate DEFAULT 2500.00, created_by, created_at/updated_at).
- `vehicles` (id, fleet_id FK NOT NULL, vehicle_number UNIQUE, make_model, tank_capacity_liters default 350.00, expected_km_per_liter default 4.00, owner_phone, created_by FK→users, is_active). `created_by` scopes vehicles to the Trip Manager / Super Admin who registered them; `fleet_id` binds the vehicle to a fleet and counts against its `vehicle_limit`.
- `trips` (id, fleet_id FK→fleets NOT NULL, trip_code UNIQUE, vehicle_id FK, vehicle_no, driver_user_id FK→users, start_odo, current_odo, end_odo, status CHECK ACTIVE/COMPLETED/SETTLED/CANCELLED, origin, destination, state_code VARCHAR(10) (operating state derived from the vehicle plate prefix via `services/state.py::state_code_from_plate`, e.g. UP32TA1234 → UP, used by the expense route to pick a per-state fuel band), verification_hash VARCHAR(32) (SHA256 fingerprint written by `settle_trip` in the same transaction that flips status), created_by FK→users, driver_user_id FK→users, created_at, completed_at, settled_at). `fleet_id` is REQUIRED for multi-tenant isolation; `created_by` is the manager who started the trip; `driver_user_id` links the assigned driver. `trip_code` is **auto-generated** by `db/queries/trips.py:insert_trip` as `{last-4-digits of vehicle_no}-{next-number for that plate}`, e.g. `1234-1`, `1234-2` (see `next_trip_code`). **driver_name/driver_phone and advance_amount/driver_batta_amount are no longer stored denormalized on trips (2026-08)**: driver identity is derived via JOIN with `users` on `driver_user_id`; cash advance & batta live only in the `expenses` ledger (`CASH_ADVANCE`/`DRIVER_SALARY` rows).
- `expenses` (id, trip_id FK→trips NOT NULL ON DELETE CASCADE, trip_code FK→trips(trip_code) ON DELETE CASCADE (2026-08), exp_type: FUEL/DEF/TOLL/REPAIR/CHALLAN/MISC/GOODS_BUY/GOODS_SALE/CASH_ADVANCE/DRIVER_SALARY, amount, approved_amount, liters, rate, odometer, station_name, state_code (fueling state the driver picks per fuel/DEF purchase — drives the band; falls back to `trips.state_code`, then `DEFAULT_BAND`), is_flagged, flag_reason, manager_status: PENDING/APPROVED/REJECTED, reviewed_by FK→users, reviewed_at, receipt_image_url, raw_receipt_text, created_at/updated_at). `trip_id` owns the trip relationship; `trip_code` is an indexed lookup column now FK-constrained to `trips(trip_code)` so it can never silently orphan. `CASH_ADVANCE`/`DRIVER_SALARY` ledger rows are auto-posted at trip creation (the single source for advance & batta). Goods buys/sales always start pending; `reviewed_by`/`reviewed_at` capture the manager audit trail.
- `fuel_benchmarks` (id, state_code UNIQUE, state_name, benchmark_price_per_liter, tolerance_pct NUMERIC(5,2) default 8.00 — percentage points, effective_date, updated_at) — per-state fuel price index for the anomaly rules engine (managed **read-only** via the Super Admin `/fuel-benchmarks` page; manual add/edit/delete was removed — the table is populated by the "Fetch Live Rates" sync). `updated_at` is bumped by the `trg_fuel_benchmarks_updated_at` trigger; the "Fetch Live Rates" button (`POST /api/v1/benchmarks/sync-live`, Super Admin / Trip Manager) upserts live state prices by `state_code` from `services/fuel_live.py` (goodreturns page with a browser User-Agent, falling back to a maintained static snapshot). `state_code` is UNIQUE so the upsert can `ON CONFLICT (state_code) DO UPDATE`.
- `webhook_logs` (id, event_id UNIQUE, event_type, payload JSONB, status: PROCESSED/SKIPPED/FAILED, processed_at, created_at) — Razorpay webhook deduplication ledger. The `/billing/webhook` handler writes a row keyed by the stable Razorpay `event.id` *inside the same transaction* that applies the event's side effect, so a retried delivery cannot activate a plan / bump a vehicle limit twice. Backed by `db/queries/billing.py`. Defined natively in `/database/schema.sql` (table #8); legacy databases catch up via `/database/incremental.sql` (the only reconciliation step — no app-run migrations exist).
- `error_logs` (id, method, path, status_code, error_type: API_ERROR/VALIDATION/HTTP_ERROR/INTERNAL, message, detail TEXT (JSON), traceback_text, endpoint, source: BACKEND/PAYMENT/WHATSAPP/WEBHOOK default BACKEND, created_at) — **central sink for every backend error.** Global exception handlers (see `backend/app/core/errors.py`, registered in `main.py` via `register_error_handlers`) catch `ApiError`, `RequestValidationError`, `HTTPException`, and any uncaught 5xx, normalize them to `{error, code}` JSON, and persist a row here. `deps._bad`/`_not_found` now **raise** `ApiError` so all existing `return _bad(...)`/`_not_found(...)` call sites log through this table. Logging is best-effort (a broken DB never breaks the request). Defined natively in `/database/schema.sql` (table #9) and idempotently in `/database/incremental.sql`. **Routing-miss noise guard:** 404/405 responses are NOT persisted (neither for plain routing misses via `_handle_http_error` nor for `ApiError`-raised not-found like `GET /trips/NOPE` via `_handle_api_error`) — the client still gets the same 404 JSON, but junk/probe requests no longer flood the table.

> `require_json_auth`/`require_json_role` → 401/403 JSON). There is no separate

### `backend/app/api/*` (security-hardened, all -guarded unless noted)

> ⚠️ **This subsection mixes two eras.** Entries pointing at flat `api/<name>.py` router modules (`views.py`, `rule_engine.py`, `dashboards.py`, `drivers.py`, and the legacy flat `users/fleets/billing/benchmarks/settlement.py` routers) are **historical — removed 2026-07**: none of those module files exist in the current tree (`backend/app/api/` holds only `v1/` domain routers + `webhook.py`). The live surface is the `/api/v1/*` entries below (plus `POST /billing/webhook` and `/healthz` in `main.py`).
- `GET /login`, `POST /login`, `GET /logout` — `api/auth.py`: TTL sessions via `create_session`, per-IP brute-force lockout, secure cookie (httponly, samesite=lax). Wrong password → `303 /login?error=1`. `GET /login` is public.
- `POST /create-trip` — `api/trips.py`: inserts `trips` row (validates plate regex, `+91` phone, non-negative advance/odo; blocked if another ACTIVE trip exists). The `trip_code` is **auto-generated** from the vehicle plate's last-4 digits (`insert_trip` / `next_trip_code`). Captures `created_by` (logged-in manager), `driver_user_id` + `vehicle_id` from the Start-Trip modal dropdowns.
- `GET /settle-trip?trip_code=` — `api/trips.py`: marks trip `SETTLED` (only when no PENDING expenses remain).
- `POST /api/v1/expenses` — `api/api_v1.py`: runs `evaluate_expense()` then inserts an `expenses` row (goods stay pending; flagged → pending); upserts `trips.current_odo`. Backs the **driver Driver (WhatsApp)** view (DriverWhatsApp.jsx). Guards: any authenticated user, but scoped to the trip's fleet & ownership (`_trip_forbidden`). This **replaces** the legacy `POST /simulate-whatsapp` (removed — returns 404/405).
- `POST /api/v1/expenses/{id}/action` — `api/api_v1.py`: manager decision (APPROVE/REJECT) on a flagged/pending expense or goods transaction. Role-guarded to `trip_manager`/`super_admin` + fleet-scoped. Backs the **manager WhatsApp escalation** view (ManagerWhatsApp.jsx) alongside `GET /api/v1/whatsapp/escalations`. This **replaces** the legacy `GET /action-expense` (removed — returns 404/405).
- `GET /fleets` + `GET /fleets/create`, `POST /fleets/create`, `GET /fleets/edit/{id}`, `POST /fleets/edit/{id}`, `GET /fleets/deactivate/{id}`, `GET /fleets/activate/{id}` — `api/fleets.py`: **Fleet CRUD** (Super Admin only). Creates a fleet that starts a 15-day trial with 1 vehicle. Shows subscription status, plan, and vehicle count.
- `GET /billing/overview` + `POST /billing/subscribe` + `POST /billing/renew/{plan_code}` — `api/billing.py`: **Subscription** management. `GET /overview` reads plans from the `subscription_plans` catalogue table (single source of truth) and returns the caller's fleet state + available plans. `POST /subscribe` activates TRIAL (restarts trial clock) or creates a Razorpay payment link for MONTHLY/YEARLY. `POST /renew/{plan_code}` creates a renewal payment link (same Razorpay reference_id format as subscribe so the webhook handles it). All POSTs audited in `fleet_billing_events`.
- `GET /billing/vehicle-slot` + `POST /billing/vehicle-slot` — `api/billing.py`: purchase additional vehicle slot when fleet hits its cap (Razorpay payment link, audited).
- `GET /fleets/subscriptions` — `api/billing.py`: **Super Admin** consolidated table of all fleets with plan name, subscription status, vehicle usage, next billing date, trial end, and renewal actions.
- `POST /billing/webhook` — `api/billing.py`: Razorpay server→server callback (HMAC-SHA256 signature verified). Handles `payment_link.paid`. **Idempotent by design**: each event is recorded in `webhook_logs` (UNIQUE `event_id`) inside the same transaction that applies its side effect, so a retried delivery can never activate a plan / bump a vehicle limit twice.
- `GET /dashboard` — `api/dashboard.py`: -only savings dashboard (money-saved/claimed/approved/**pending** cards + per-trip Chart.js bar chart); fallback landing page. **Role-scoped**: trip_manager sees only their own trips' figures, driver only their assigned trips, super_admin sees all.
- `GET /admin` — `api/dashboards.py`: **Super Admin** macro dashboard (role-gated via `require_role(..., "super_admin")`): Active Fleet, Fuel & Road Spend (MTD), Leakage Prevented (REJECTED sum), Outstanding Cash Float; anomaly heatmap, km/L-efficiency leaderboard vs. `vehicles.expected_km_per_liter`, settlement approval summary + quick actions. Query helpers in `db/queries/dashboards.py`.
- `GET /manager` — `api/dashboards.py`: **Trip Manager** dashboard (`require_role("trip_manager","super_admin")`): dispatched trips, pending escalations, advances disbursed today, awaiting-settlement count; live escalation feed with 1-click Approve/Deduct (`/action-expense`), active-trip progress table, 1-click settlement queue. **All figures scoped to trips the logged-in manager created** (`manager_kpis`/`open_escalations`/`active_trip_progress` filter by `created_by`; the unused `settlement_ready_trips` was later **deleted** from `db/queries/dashboards.py` — 2026-08 dead-code cleanup); super_admin sees everything.
- `GET /driver` — `api/dashboards.py`: **Driver** dashboard (`require_role("driver")`): live status card (active trip, advance, cash-in-hand = advance + approved net, logged-today), quick-log actions, recent expense logs + trip-end summary.
- `POST /login` redirects by role to the legacy HTML path (`super_admin → /admin`, `trip_manager → /manager`, `driver → /driver`). **The React SPA deliberately ignores this**: `AuthContext.login()` normalizes every role onto the SPA `/dashboard` route so the app never full-page-loads to the server-rendered `/admin`/`/manager`/`/driver` pages (which previously hard-redirected a driver to `https://app.vahankhata.in/driver`). `App.jsx` also maps `/admin`, `/manager`, `/driver` → `/dashboard` for direct-URL access inside the SPA (those redirect shims were **removed** from `App.jsx` in the 2026-08 dead-code cleanup).
- `GET /` — `api/views.py`: 3-column dual-WhatsApp workspace UI (see UI Layout below); **scoped** so a manager/driver can only open their own trips. The Start New Trip modal loads **Vehicle Number + Driver dropdowns** populated from the manager's registered vehicles (by `created_by`) and the active driver accounts.
- `GET /vehicles` + `GET /vehicles/create`, `POST /vehicles/create`, `GET /vehicles/edit/{id}`, `POST /vehicles/edit/{id}`, `GET /vehicles/deactivate/{id}`, `GET /vehicles/activate/{id}` — `api/vehicles.py`: **Vehicle CRUD** (role-gated to `trip_manager`/`super_admin`). Managers see/register only the vehicles they created (`created_by`), and these feed the Vehicle Number dropdown in the Start-Trip modal. Plates validated against the regex.
- `GET /trips` — `api/views.py`: trip listing (active first) with per-trip expense totals / pending counts; **scoped by role** — a trip_manager only sees trips they created (`created_by`), a driver only their assigned trips, super_admin sees all. "Start New Trip" disabled while a trip is active. **`GET /` with no args 303-redirects here**, so the listing is the single table-view entry point (no duplicate root handlers).
- `GET /fuel-benchmarks` + `POST /fuel-benchmarks/add`, `POST /fuel-benchmarks/edit`, `GET /fuel-benchmarks/delete?id=` — `api/benchmarks.py`:  CRUD for per-state fuel price benchmarks.
- ~~`GET /rule-engine`~~ (`api/rule_engine.py`) — **fully removed**. This flat module never existed post-JSON-migration, its explainer content lives on the Rules & Rates `/benchmarks` page (`GET /api/v1/benchmarks`), and the later SPA `/rule-engine` page + `GET /api/v1/rules` endpoint were themselves deleted (2026-08 dead-code cleanup).
- `GET /settled-pdfs` — `api/settlement.py`: lists settled trips with links to their settlement PDFs (scoped to the caller's own trips).
- `GET /drivers` + `GET /drivers/create`, `POST /drivers/create`, `GET /drivers/edit/{id}`, `POST /drivers/edit/{id}`, `GET /drivers/deactivate/{id}`, `GET /drivers/activate/{id}` — `api/drivers.py`: **Driver CRUD** (role-gated to `trip_manager`/`super_admin`). Create/edit forms set the driver **batta profile** (`batta_type` + `default_batta_rate`); the listing shows a Batta column. Trip creation snapshots the resolved batta onto `trips.driver_batta_amount`.
- `GET /generate-settlement-pdf?trip_code=` — `api/settlement.py`: builds a reportlab PDF settlement/reconciliation sheet via `services/pdf/settlement.py` (default renderer). **Optional WeasyPrint renderer** (`renderer="weasyprint"` param on `build_settlement_pdf`) renders the same data through the Jinja2 template `services/pdf/templates/settlement_voucher.html`; it needs Pango/HarfBuzz native libs (Linux: `apt-get install libpango-1.0-0 libharfbuzz0b`) and degrades gracefully to reportlab if those are absent.

For driver users the create/edit forms + JSON API also set the **batta profile** (`batta_type` FIXED_TRIP/PER_KM/DAILY/NONE + `default_batta_rate`, default ₹2,500). `POST /users/create` fires the same manager onboarding email as the JSON API. `GET /users/change-password` — Super Admin (and any role) shows the logged-in user's password change form (no DB); `POST /users/change-password` handles its submission.
- `GET /api/v1/auth/login` (*POST*) — `api/api_v1.py` + `api/auth.py`: JSON login returning `{"token", "user", "landing"}` + optional `ff_auth_session` cookie. 401 invalid creds, 423 locked, 403 inactive. **Transport-agnostic (Bearer or cookie) — for React SPA + mobile.**
- `GET /api/v1/auth/me` — `api/auth.py`: returns current session user JSON, or **401 JSON** (never 303). Cookie or Bearer.
- `GET /api/v1/dashboard/overview` — `api/api_v1.py`: role-aware dashboard payload (admin_kpis / manager_kpis+active_trips+escalations / driver trip+balances). 401 JSON when unauthenticated.
- `GET /api/v1/trips`, `GET /api/v1/trips/{trip_code}` — `api/api_v1.py`: role-scoped trip list (+ per-trip stats) and a trip detail with its expenses. Ownership-guarded (403 for cross-scope). 401 JSON when unauthenticated.
- `POST /api/v1/trips` — `api/api_v1.py`: create/start a trip (trip_manager/super_admin). Accepts `vehicle_no`, `vehicle_id`, `driver_user_id`, `advance_amount`, `start_odo`. Validates plate regex, non-negative advance/odo; resolves driver name/phone/batta from `users` via `driver_user_id`; resolves tenant fleet; blocks if an active trip exists (409). The `trip_code` is **auto-generated** (`{last4-of-plate}-{next-number}`); no client-supplied code is accepted. 201 on success returns the generated `trip_code`.
- `POST /api/v1/trips/{trip_code}/settle` — `api/api_v1.py`: settle a trip (manager/super_admin). 409 if pending expenses remain; 403 for cross-scope managers. The manager's settle is also an **implicit consent** (Option 1): the authenticated manager id is stamped onto `trips.manager_consent_by/_at` in the same transaction, so the printed voucher's bilingual "Manager Acceptance" line has an auditable name + timestamp. The driver consents explicitly via WhatsApp (single webhook sends a consent keyword e.g. `CONSENT`/`स्वीकृत`; the sender's phone is authenticated and the driver's active trip receives `driver_consent_by/_at`). Both consent rows are server-authoritative (DB `CURRENT_TIMESTAMP`) and `COALESCE`-idempotent (first consent wins).
- `GET /api/v1/settlements` — `api/api_v1.py`: role-scoped list of SETTLED trips for the PDF listing.
- `GET /api/v1/driver/salary` — `api/api_v1.py`: **read-only** driver salary/batta summary for the logged-in driver (`require_json_role("driver")`). Returns the driver's batta profile + per-trip settlement breakdown (batta, net payable/refund) for their own assigned trips, plus totals. Powers the **Driver Salary** SPA page.
- `GET /api/v1/settlements/{trip_code}/pdf` — `api/api_v1.py`: streams the settlement PDF (`application/pdf`, inline) via `services/pdf/settlement.py`. Ownership-guarded 403. The bilingual (English/Hindi Devanagari) voucher renders via the bundled **static** `NotoSansDevanagari-Regular.ttf` (SIL OFL, see `OFL.txt` next to it) registered in `settlement.py` — reportlab's default Helvetica has no Devanagari glyphs. The bundle is the notofonts **v2.006 hinted full static instance**, which carries **both** scripts (GF-Latin-core A–Z/a–z + digits/punct + ₹ + full Devanagari block): an earlier script-only Noto build had *zero* Latin letterforms, so every English word painted as blank `.notdef` while digits/Hindi still rendered (`21-Aug-2026` → `21--2026`) — guarded by `tests/unit/test_settlement_pdf.py::test_bundled_font_covers_latin_letters` + `test_build_settlement_pdf_embeds_latin_glyphs`. A **static** (non-variable) instance is used deliberately: variable fonts lack an `fvar`-free fixed geometry and can break Pillow/headless image renderers, so this one bundled asset stays compatible with both reportlab PDFs and any future sticker/image capture. Because reportlab does NOT shape complex scripts natively, `_hi_style()` sets `shaping=True` (reportlab 5.x routes text through HarfBuzz via `uharfbuzz`, a new `requirements.txt` dep). This performs the GSUB/GPOS work that turns broken Devanagari (`विवरण`→`वविरण`, `ट्रिप`→`टरपि`) into correctly engaged conjuncts + repositioned pre-base matras. Labels also join via the `_bi(en, hi)` helper so an empty/missing language key can never emit an orphaned slash (`/ यात्रा हिसाब पर्ची`).
- `POST /api/v1/expenses` — `api/api_v1.py`: JSON expense log (runs `evaluate_expense`, sets manager_status, upserts odometer). **No single-use CSRF** (React parallel-safe). 201 on success, 400 invalid type, 404 trip not active. The FUEL price band is resolved from the driver-submitted **fueling state** (`expenses.state_code`), falling back to `trips.state_code`, then `DEFAULT_BAND`; so refreshed live rates are immediately enforced and a UP truck fueling in MP is judged against MP's benchmark.
- `POST /api/v1/expenses/{id}/action` — `api/api_v1.py`: JSON approve/reject.
- `GET/POST /api/v1/vehicles`, `PUT /api/v1/vehicles/{vid}`, `POST /api/v1/vehicles/{vid}/toggle` — `api/api_v1.py`: Vehicle CRUD (trip_manager/super_admin). Create enforces the fleet subscription vehicle limit (402) + plate regex + duplicate check; 403/404 for cross-scope.
- `GET/POST /api/v1/users`, `PUT /api/v1/users/{uid}`, `POST /api/v1/users/{uid}/toggle` — `api/api_v1.py`: User CRUD (Super Admin). Password hashed on create/update; `password_hash` always stripped from responses; 403/404 guards. **Creating a Trip Manager fires the manager onboarding email** via `services/email/client.py::send_manager_onboarding_email_sync` (fire-and-forget; no-op when Resend unconfigured). - `POST /api/v1/auth/change-password` — `api/api_v1.py`: JSON mirror of the HTML change-password flow (any authenticated role, self-service). Verifies current password, enforces min 4 chars + confirm-match, hashes + updates the logged-in user. 401 unauthenticated, 400 `WRONG_PASSWORD`/`WEAK_PASSWORD`/`PASSWORD_MISMATCH`.

- `POST /api/v1/auth/login`, `GET /api/v1/auth/me`, `POST /api/v1/auth/logout` — `api/api_v1.py`: JSON auth (login returns `{token,user,landing}`; me/logout return JSON). `POST /api/v1/auth/login` accepts a browser-JSON or form-encoded body.

Powers the **Billing** SPA page. (The SPA redirects the browser to the returned Razorpay URL.)

### Settlement / Unified Ledger (trip creation auto-posts two fixed provisions)
- `POST /api/v1/trips` now auto-posts two `APPROVED` expense rows as the trip's opening ledger entries: `CASH_ADVANCE` (owner cash-in-advance, credit) and `DRIVER_SALARY` (driver batta, debit). These are fixed provisions so they bypass the rules engine (never flagged). Advance & batta are therefore captured once, in the **expenses ledger** — the single source for managers and the driver (Driver Salary page, TripDetail expense table, WhatsApp stats).
- `compute_settlement` (`backend/app/services/audit/cash.py`) derives `advance_amount` and `driver_batta` **solely** from the trip's `APPROVED` `CASH_ADVANCE`/`DRIVER_SALARY` ledger rows — the single source of truth; there is no `trips`-column fallback (legacy rows were backfilled by the 2026-08 normalization migration). Net = advance + goods_income − (road expenses + driver batta).
- **SETTLEMENT_TRANSFER closing entry (2026-08, driver acceptance v2):** drivers record acceptance from `/whatsapp-driver` (`TripWhatsApp.jsx` → `POST /api/v1/expenses`, `exp_type=SETTLEMENT_TRANSFER`). The row IS the cash-handover closing entry: amount is server-computed `|net_balance|` (client value ignored, returned as `settlement_amount`), starts PENDING, and **locks the expense ledger** until the manager resolves it (`409 SETTLEMENT_LOCKED`; duplicate live request → `409 SETTLEMENT_ALREADY_INITIATED`; assigned-driver-only + ACTIVE trip only, else 403). Manager **Approve** on it first re-verifies the balance (`409 LEDGER_CHANGED` on drift), flips it APPROVED, and **stamps `trips.driver_consent_by/_at`** (first-wins via existing `driver_consent`) — this populates the voucher's Driver Acceptance row; the WhatsApp `CONSENT`-keyword path still works but is no longer required. `compute_settlement` applies an APPROVED transfer side-aware (pre-net > 0 → DR driver-returns; < 0 → CR fleet-pays) so **Dr/Cr net to ₹0.00 / FULLY SETTLED**, appends `|transfer|` to the verification-hash input only when a transfer exists (legacy stored voucher codes stay byte-stable), and exposes `settlement_transfer`/`settlement_transfer_side` — rendered as a bilingual "Cash Settlement Transfer / निपटान रोकड़ भुगतान" Dr/Cr row + "Paid & Accepted" callout in BOTH PDF renderers (reportlab `_render_pdf` + WeasyPrint template/context). Dashboard KPI queries (`dashboards.py`) force `approved_net`/cash-in-hand to 0 once an APPROVED transfer exists and exclude the type from leakage-prevented, logged-today and claimed sums. Rejection frees the ledger so the driver can log missed expenses and re-initiate (old REJECTED rows kept for audit). Schema: `expenses.exp_type` CHECK now includes `SETTLEMENT_TRANSFER` (`database/schema.sql` + idempotent constraint swap appended to `database/incremental_ddl.sql`). Tests: `tests/unit/test_settlement_netting.py` (closing-entry math + hash stability) and `tests/unit/test_settlement_transfer_api.py` (guardrails, lock, consent stamp, LEDGER_CHANGED).
